# 系统总体架构设计

> 版本：v1.0　编写日期：2026-11-25　状态：待确认

## 一、设计目标与约束

### 目标
让用户只面对"一个 AI 研发总监"，由它完成需求理解、任务拆解、Agent 选择、执行监督、结果验收与汇报。

### 硬约束（来自需求）
1. 所有 Agent 与构建必须在 WSL Ubuntu Native 执行，禁止副本、禁止 Windows 路径。
2. 微信是主入口，Web 是配置/监控/审计入口。
3. 微信消息必须先进 Hub，不得绕过总指挥直达 Agent。
4. 模块化单体，前后端分离。
5. 不允许"假实现"：无 Mock 冒充、无 TODO 占位、无静态假数据。

### 由环境推导出的约束（本次新增）
6. **WSL 内 Agent 必须重新安装 Linux 原生版本**，`/mnt/*` 下的 Windows shim 一律视为"未安装"。
7. **ACP 客户端自研**（中央仓库无 Java SDK）。
8. **双 JDK 共存**：Hub=21，PMS=17，执行期按项目注入。

## 三、核心链路时序

### 3.1 微信任务全链路

```
用户           WeClaw            hub-channel       Commander        hub-task      hub-runtime      Agent
 │               │                   │                │                │              │             │
 ├─"检查PMS有无Bug"─▶                │                │                │              │             │
 │               ├─POST /v1/chat────▶│                │                │              │             │
 │               │                   ├─白名单校验      │                │              │             │
 │               │                   ├─会话定位        │                │              │             │
 │               │                   ├─幂等去重        │                │              │             │
 │               │                   ├─受理确认────────┼───────────────▶│              │             │
 │               │◀──"收到，正在分析"─┤                │                │              │             │
 │               │                   ├─调度请求───────▶│                │              │             │
 │               │                   │                ├─意图+项目识别   │              │             │
 │               │                   │                ├─创建任务────────▶              │             │
 │               │                   │                ├─匹配 Agent      │              │             │
 │               │                   │                ├─派发────────────┼─────────────▶│             │
 │               │                   │                │                │              ├─建 Worktree │
 │               │                   │                │                │              ├─ACP 会话────▶│
 │               │                   │                │                │              │◀─流式更新────┤
 │               │                   │                │◀──进度事件──────┤              │             │
 │               │◀──"已分配 Claude"──┼────────────────┤                │              │             │
 │               │                   │                │                │              ├─构建/测试    │
 │               │                   │                │◀──执行结果──────┤              │             │
 │               │                   │                ├─Diff 校验       │              │             │
 │               │                   │                ├─必要则复核──────┼─────────────▶│             │
 │               │◀──最终报告─────────┼────────────────┤                │              │             │
 │               │                   │                ├─状态→SUCCESS    │              │             │
```

**关键设计点**

- **HTTP 请求不阻塞到任务结束**。`/v1/chat/completions` 在 2 秒内返回"受理"文本并结束（非 stream）或先吐一句再结束（stream）。后续进度全部由 Hub 通过 WeClaw `POST /api/send` 主动推送。这是需求"对长时间任务采用异步任务机制，不得无限阻塞 HTTP 请求"的落地点。
- **幂等**：WeClaw 的请求若带唯一 message id 则用它；否则用 `hash(sender + text + 分钟级时间窗)` 做去重，表 `hub_channel_message` 唯一索引兜底。
- **进度推送去抖**：Agent 的流式增量合并为 3 秒窗口，避免刷屏微信。

### 3.2 调度决策流程

```
任务入队
   │
   ├─ 1. 硬过滤：能力匹配（capability ∩ task.type ≠ ∅）
   │             状态 ∈ {ONLINE, BUSY(有并发余量)}
   │             项目要求的协议/工具链具备
   │
   ├─ 2. 打分（0~100）：score = w1·能力匹配度 + w2·历史成功率
   │                          − w3·当前负载率 − w4·预估成本
   │                          + w5·用户偏好加成
   │     默认权重 w=[35,25,20,10,10]，可在 hub_schedule_rule 调整
   │
   ├─ 3. 无候选 → 判定：排队等待 / 明确拒绝（告知原因，不假装成功）
   │
   ├─ 4. 选中 → 写 hub_task_agent + hub_task_log(decision)
   │     决策理由必须落库：候选集、各候选得分、淘汰原因、最终选择
   │
   └─ 5. 执行中失败 → 按 retry_policy：
           同 Agent 重试（≤N 次，指数退避）→ 换 Agent → 人工介入
```

### 3.3 任务状态机

```
CREATED ──▶ ANALYZING ──▶ QUEUED ──▶ RUNNING ──▶ VERIFYING ──▶ SUCCESS
   │            │            │          │            │
   │            │            │          │            └──▶ FAILED
   │            │            │          └──▶ PAUSED ──▶ RUNNING
   │            │            └──▶ CANCELLED
   │            └──▶ WAITING_APPROVAL ──▶ QUEUED
   └──▶ CANCELLED
```
- 终态：`SUCCESS` / `FAILED` / `CANCELLED`。
- 所有迁移走单一入口 `TaskStateMachine.transit(taskId, from, to, reason)`，带乐观锁 `version`，非法迁移抛 `IllegalTransitionException`。
- 每次迁移写 `hub_task_log`（type=STATE）。

## 四、模块边界与依赖

```
hub-server（启动装配，唯一有 main）
   └── 依赖全部业务模块

hub-web ──▶ hub-task, hub-agent, hub-project, hub-approval, hub-memory, hub-monitor, hub-system
hub-channel ──▶ hub-task（只提交调度请求）, hub-agent（只读状态）, hub-system
hub-task ──▶ hub-agent, hub-project, hub-approval, hub-memory, hub-runtime
hub-agent ──▶ hub-runtime（进程启停）
hub-project ──▶ hub-runtime（路径校验）
hub-runtime ──▶ hub-common（无业务依赖，可独立测试）
hub-monitor ──▶ 全部模块（只读聚合）
hub-common / hub-security / hub-system：底层，不被反向依赖
```

**依赖规则（强制，构建期用 ArchUnit 守护）**
- 禁止 `hub-runtime` 依赖任何业务模块（保证执行引擎可独立演进）。
- 禁止模块间循环依赖。
- `hub-common` 不得依赖 Spring Web（保持纯工具）。
- 跨模块调用只走 Service 接口，不直接访问他模块 Mapper。

## 五、关键抽象

### 5.1 AgentAdapter（统一 Agent 接入）

```java
public interface AgentAdapter {
    AgentType type();                                   // CLAUDE_CODE / CODEX / OPENCODE / CUSTOM
    ProbeResult probe();                                // 安装/版本/认证/ACP 可用性
    AgentSession openSession(SessionSpec spec);         // 建立会话（含 cwd、权限模式）
    void prompt(AgentSession s, PromptRequest req, Consumer<AgentEvent> sink);
    void cancel(AgentSession s);
    void close(AgentSession s);
}
```

三个实现：
- `AcpAgentAdapter`：stdio JSON-RPC，主路线（Claude / Codex / OpenCode）。
- `CliAgentAdapter`：`claude -p` / `codex exec`，每消息一进程，`--resume` 续会话（ACP 不可用时的降级）。
- `HttpAgentAdapter`：OpenAI 兼容端点（兼容 WeClaw 风格的外部 Agent）。

**不允许"把 Agent 当普通 Shell 命令"**：`CliAgentAdapter` 也必须是结构化解析（JSON 事件流），不能 `ProcessBuilder("bash","-c",userText)`。

### 5.2 ExecutionContext（执行上下文）

```java
record ExecutionContext(
    String taskId, Path worktree, Path projectRoot,
    String jdkHome,           // 双 JDK 关键：按项目注入
    String nodeVersion,
    Map<String,String> env,   // 过滤后的白名单环境变量
    Duration hardTimeout,
    ApprovalPolicy approval   // 危险动作的放行策略
) {}
```

### 5.3 记忆分层

| 层 | 载体 | 检索方式 | 注入时机 |
| --- | --- | --- | --- |
| 用户记忆 | `hub_memory`(scope=USER) + `identity/memory/user-*.md` | 关键词 + 最近 N 条 | 每次会话首轮 |
| 项目记忆 | `hub_memory`(scope=PROJECT) + 项目根 `HUB_MEMORY.md`（已存在则只读追加） | 项目定位后 | 任务开始前 |
| Agent 记忆 | `hub_memory`(scope=AGENT) | Agent 选中后 | 组装 prompt 时 |
| 任务记忆 | `hub_task` + `hub_task_log` | 相似任务 top-k | 拆解阶段 |
| 系统记忆 | `hub_memory`(scope=SYSTEM) | 全量加载 | 常驻系统提示 |

## 六、并发与可靠性

| 关注点 | 方案 |
| --- | --- |
| Agent 并发上限 | `agent_registry.max_concurrency` + Redis 信号量 `agent:slot:{id}` |
| 任务队列 | Redis ZSET（优先级 + 入队时间），DB 为真相源，启动时对账 |
| 分布式锁 | Redisson，锁 key `task:{id}:exec`，TTL 30 min + 看门狗 |
| 任务幂等 | `hub_task.request_id` 唯一索引 |
| 进程孤儿 | 每次启动扫描 `hub_task` 中 RUNNING 且 pid 不在 `hub_task_process` 的任务 → 置 FAILED(orphan) |
| 服务重启恢复 | 任务状态从 DB 恢复；RUNNING 的按 `resume_policy` 决定重跑或转 FAILED |
| 超时 | 空闲超时（无事件 5 min）/ 硬超时（默认 60 min，按任务类型可配） |
| 日志轮转 | logback 按天 + 100 MB 滚动，保留 30 天；任务日志 ≥64 KB 转文件 |

## 七、扩展点

| 扩展 | 机制 |
| --- | --- |
| 新 Agent | 实现 `AgentAdapter` + 在 `agent_registry` 插一条 `agent_type=CUSTOM` + 配置启动命令 |
| 新渠道（企微/飞书） | 实现 `ChannelInbound/ChannelOutbound` 接口，注册到 `hub_channel` |
| 新工作流引擎（LoopForge） | `WorkflowEngine` SPI，默认实现 `SingleTaskWorkflow` |
| 语义检索 | `MemoryRetriever` 接口，默认 `KeywordRetriever`，后续可换 pgvector |
| 新 LLM | `LlmProvider` 接口 + `hub_system_config` 热切换 |
