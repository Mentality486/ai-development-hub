# 项目可行性分析

> 版本：v1.0　编写日期：2026-11-25　状态：待确认
> 本文所有"实测"结论均来自 2026-11-25 在本机 WSL Ubuntu-24.04 中的实际命令输出，未实测的部分明确标注为"待验证"。

---

## 一、结论摘要

| 维度 | 结论 |
| --- | --- |
| 整体可行性 | **可行**。目标是"本地多 Agent 协同研发管理"，不涉及不可控的第三方云服务，核心链路（消息 → 总指挥 → Agent → 验收 → 回报）都可以在本机打通。 |
| 最大阻塞项 | **WSL 内没有任何 Linux 原生 Agent**。`claude`/`codex`/`gemini` 命中的是 Windows 侧 nvm 下的 shell shim，在 Linux 里执行直接报 `Exec format error`。必须重新安装 Linux 原生版本并重新授权。 |
| 第二阻塞项 | **Maven 中央仓库没有官方 Java ACP SDK**（实测检索 0 条）。ACP 客户端必须自行实现，工作量需要计入计划，不能假设"引个依赖就有"。 |
| 第三阻塞项 | **JDK 21 未安装**（当前仅 17）。项目要求 JDK 21，需安装并处理"Hub 用 21、PMS 用 17"的双 JDK 并存。 |
| 需产品侧确认 | 微信侧能否拿到稳定的"发送者标识"决定会话隔离的粒度；WeClaw HTTP Agent 模式的请求体格式**尚未实测**，是第六阶段的关键前置验证项。 |

### 2.3 数据存储

| 组件 | 实测 | 判定 |
| --- | --- | --- |
| 本地 MySQL | **未安装**（`mysql` 命令不存在，3306 无监听）；`mysql-server` 可 apt 安装 | ❌ 需部署 |

| 私有 Maven 仓库 | `~/.m2/settings.xml` 配置 `nexus` → `http://10.7.0.185:8081/repository/maven-public/`，`mirrorOf=*` | ✅ 全部依赖走私有库，已有 12 GB 本地缓存 |

**判定：Hub 必须使用独立的 MySQL 8 + Redis 7 实例**（本地 WSL 部署，独立库 `ai_hub`）。理由：需求第十条禁止擅自修改用户已有项目配置；且 PMS 库被其 CI 与本地开发共同使用，混用会互相污染。10.7.0.185 仅作为"网络可达性"证据，不作为 Hub 的数据源。

### 2.4 Agent 现状（最关键的缺口）

| Agent | PATH 命中 | 实际可用性 |
| --- | --- | --- |
| claude | `/mnt/d/ProgramFiles/nvm/nodejs/claude` | ❌ 是 Windows nvm 的 shell shim，指向 `claude.exe`，Linux 下报 `Exec format error` |
| codex | `/mnt/d/ProgramFiles/nvm/nodejs/codex` | ❌ 同上，运行即抛 JS 异常（平台判定失败） |
| gemini | `/mnt/d/ProgramFiles/nvm/nodejs/gemini` | ❌ 同上 |
| opencode | 未找到 | ❌ 未安装 |
| aider / qwen / crush | 未找到 | ❌ 未安装 |
| Agent 凭据目录 | `~/.claude`、`~/.codex`、`~/.opencode`、`~/.claude.json` **全部不存在** | ❌ WSL 内从未授权过 |
| npm 全局包 | `~/.npm-global/lib` 为空 | ❌ |

**结论：第一阶段的"自动发现"必须能正确识别并如实报告这种状态**——这正是需求模块二强调"不能仅凭 which 判断在线"的现实理由：本机 `which claude` 有输出，但 Agent 完全不可用。发现流程必须做到"可执行文件存在 → 能在本环境跑起来 → 通过 ACP 握手"，三级递进。

**修复方案（Linux 原生安装，需用户配合重新登录授权）：**

```bash
# Claude Code（原生 Linux）
npm i -g @anthropic-ai/claude-code        # 实测 registry 最新 2.1.332
claude          # 首次需人工登录授权

# Codex CLI（原生 Linux）
npm i -g @openai/codex                    # 实测 0.172.0
codex           # 首次需登录

# OpenCode
npm i -g opencode-ai                      # 实测 1.19.6；自带 `opencode acp` 子命令
```

### 2.5 ACP 生态现状

| 组件 | 实测 | 说明 |
| --- | --- | --- |
| Java ACP SDK（Maven Central） | **检索 `agent-client-protocol` / `acp-java` / `agentclientprotocol` 均 0 条** | 无官方 Java 实现 → 必须自研 ACP 客户端 |
| `@agentclientprotocol/sdk` | 2.12.0 | TS/JS 官方 SDK（可作为协议语义的对照参考） |
| `@zed-industries/agent-client-protocol` | 0.4.5 | 早期 JS 实现 |
| `@agentclientprotocol/claude-agent-acp` | 0.112.0，bin `claude-agent-acp` | Claude 的 ACP 适配器（基于 Claude Agent SDK） |
| `@zed-industries/codex-acp` | 0.16.0，bin `codex-acp` | Codex 的 ACP 适配器 |
| `codex-acp`（npm） | 1.11.0，bin `codex-acp` | 另一实现，"Run Codex as an ACP agent" |
| opencode ACP | `opencode acp` 原生子命令 | 无需额外适配器，stdio JSON-RPC |
| 本机 ACP 组件 | **全部缺失** | 需随 Agent 一并安装 |

**结论：ACP 是可行路线，但"Hub 侧客户端"要自己写。** 范围明确：JSON-RPC 2.0 over stdio、换行分隔（NDJSON）、`initialize` / `authenticate` / `session/new` / `session/load` / `session/prompt` / `session/cancel` 方法，以及 `session/update`、`session/request_permission` 通知/反向请求，文件与终端类方法可先只实现读、写两类。计划中把它列为独立工作项（第三阶段约 5 人日当量）。

### 不建议做的事

- ❌ 不要把 Hub 的数据源指向 `10.7.0.185`：那是 PMS 的库。
- ❌ 不要用 Docker 跑 Agent 执行层：需求明确禁止 Docker Sandbox 隔离副本执行。
- ❌ 不要把项目放到 `/mnt/c`、`/mnt/d`：9p 文件系统性能差且权限语义不一致，会拖慢 Maven/Node 构建并引发 `Exec format error` 类问题。
- ❌ 不要升级到 Spring Boot 4.x：本地 m2 有 4.0.x，但 MyBatis-Plus/knife4j 生态对 4.x 的适配需逐个验证，收益不足以抵消风险。选 3.5.16（实测可获取的最新 3.5.x）。

## 四、关键技术风险登记

| ID | 风险 | 可能性 | 影响 | 缓解措施 |
| --- | --- | --- | --- | --- |
| R1 | WeClaw HTTP 模式不传稳定发送者 ID，无法按微信用户隔离会话 | 中 | 中 | 第六阶段第一步先抓包验证；降级为单账号单会话；必要时用 `/v1/chat/completions` 的 `user` 字段 + 白名单单一映射 |
| R2 | WeClaw 的 ACP/CLI 模式与 Hub 的 OpenAI 兼容接口不匹配 | 低 | 高 | 只在 HTTP 模式上做集成；接口按 OpenAI 规范实现并在本地用 curl 回归 |
| R3 | ACP 协议版本漂移（各适配器实现差异） | 高 | 中 | 自研客户端只依赖稳定方法集；每次握手记录 `protocolVersion` 与 `agentCapabilities`；适配器版本锁定 |
| R4 | Agent 长时间无输出导致任务悬挂 | 高 | 中 | 心跳 + 空闲超时 + 硬超时三级；`session/cancel` 后 SIGTERM→SIGKILL 兜底 |
| R5 | 微信个人号 iLink 协议属非官方通道，存在账号风控 | 中 | 高 | 明确告知用户；仅白名单账号；限速；不做群发/营销；账号与 AI 身份在数据模型上严格分离 |
| R6 | 双 JDK（Hub 21 / PMS 17）导致构建串味 | 中 | 中 | 执行引擎按 `hub_project.jdk_version` 显式注入 `JAVA_HOME`，并在任务日志首行打印实际 JDK |
| R7 | Git worktree 与原工作区争用（同一分支被检出两次） | 中 | 低 | 每个任务新建独立分支 `hub/task-xxxxx`；禁止在原工作区执行写操作；结束即清理 |
| R8 | 大日志撑爆数据库 | 高 | 中 | 日志 >64 KB 落文件，DB 只存指针 + 首尾摘要；按月归档 |
| R9 | 部分 Agent 会执行危险命令 | 中 | 高 | 三层：Agent 侧权限模式（禁止 bypassPermissions）+ Hub 侧审批 + 命令黑名单拦截；详见《系统安全设计》 |
| R10 | GitHub raw 下载不稳定 | 高 | 低 | 脚本内置重试与镜像回退 |

### 待用户拍板的一个空白

需求通篇没有指定**总指挥所用的 LLM**。总指挥要做意图识别、任务拆解、Agent 匹配，这是核心能力，不能靠规则硬编码冒充。候选：

1. 复用 Claude（已有 Claude Code 授权）——无需额外 Key，但把"调度脑"和"执行脑"绑在同一供应商。
2. 独立配置 OpenAI 兼容端点（DeepSeek / 通义 / 自建）——解耦，但需新增 Key。
3. 本地模型（Ollama）——离线可用，但拆解质量与稳定性风险高。

建议选 1 或 2，并在 `hub_system_config` 里做成可切换的 `llm.dispatch.provider`。本文档后续按"可切换 Provider 抽象"设计，不绑定具体厂商。

5. 端口规划：Hub API `18080`、前端 dev `15173`、WeClaw `18011`、MySQL `3306`、Redis `6379` —— 是否接受？
