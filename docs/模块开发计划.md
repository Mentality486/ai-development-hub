# 模块开发计划

> 版本：v1.0　编写日期：2026-11-25　状态：待确认
> 原则：一次只做一个阶段，每阶段必须编译通过 + 测试通过 + 用户验收，才进下一阶段。不允许一次性铺开全部代码。

---

## 零、总览

| 阶段 | 名称 | 交付重心 | 前置 | 估时（人日当量） |
| --- | --- | --- | --- | --- |
| 一 | 基础工程 | 能跑起来的空壳 | P0 安装 | 5–7 |
| 二 | Agent 注册中心 | 真实发现 WSL 里的 Agent | P1 安装 | 6–8 |
| 三 | ACP 通信与单 Agent 执行 | 真能指挥一个 Agent 干活 | 阶段二 | 10–14（含自研 ACP 客户端） |
| 四 | 任务调度中心 | 一人管多 Agent | 阶段三 | 8–10 |

> 估时按"熟练单人"折算，仅用于排优先级，不作承诺。不可压缩的是阶段顺序与验收门槛。

## 阶段一：基础工程

### 目标
一个能启动、能登录、能读写数据库、前后端能通信的骨架。**不含任何业务逻辑。**

### 任务分解

| # | 任务 | 关键产出 |
| --- | --- | --- |
| 1.1 | 安装 P0 依赖 | JDK 21、MySQL 8、Redis 7、Git 身份 |
| 1.2 | Maven 多模块骨架 | 父 POM + 13 个 `hub-*` 子模块，`mvn -T 1C compile` 通过 |
| 1.3 | 统一响应/异常/日志 | `R<T>`、`GlobalExceptionHandler`、`BizException`、日志 JSON 格式 |
| 1.4 | Flyway 建库 | `V1__sys_auth.sql` 起，21 张表逐步落地（阶段一只建权限域 + 配置域） |
| 1.5 | 认证 | 登录/刷新/登出、JWT、BCrypt、Redis 黑名单 |
| 1.6 | RBAC | 角色/权限表 + `@PreAuthorize` |
| 1.7 | 前端骨架 | Vite + TS + Element Plus + Pinia + Router，登录页 + 布局 + 空 Dashboard |
| 1.8 | 前后端联调 | Axios 拦截器、401 跳登录、dev 代理 |
| 1.9 | 工程规范文档 | `docs/开发规范.md`、`README.md`、`.env.example` |

### 验收标准（可执行）
```bash
# 后端
cd ai-development-hub && mvn -T 1C clean compile           # 必须 BUILD SUCCESS
mvn -pl hub-server test                                     # 至少 1 个测试通过
mvn -pl hub-server spring-boot:run &                        # 端口 18080
curl -s localhost:18080/actuator/health | jq .status         # "UP"

# 数据库
mysql -uai_hub -p -e "use ai_hub; show tables;"              # ≥7 张表

# 前端
cd frontend && npm ci && npm run build && npm run dev        # 15173 可访问
# 手工：登录 → 进 Dashboard → 刷新页面仍保持登录 → 登出回登录页
```

### 明确不做
Agent、任务、项目、微信、记忆的任何业务代码。Dashboard 只显示"模块开发中"，**不允许放假数据图表**。

## 阶段二：Agent 注册中心

### 目标
启动时自动发现 WSL 环境里的 Claude Code / Codex / OpenCode，正确区分九种状态，能手动健康检查。

### 任务分解

| # | 任务 | 关键产出 |
| --- | --- | --- |
| 2.1 | 安装 P1 依赖 | Linux 原生三件套 + ACP 适配器 + 人工授权 |
| 2.2 | `AgentProbe` | 可执行性探测（试运行 `--version`，解析 stderr）、凭据探测、ACP 探测 |
| 2.3 | `AgentAdapter` 抽象 | 接口 + `CliAgentAdapter`（先做，简单） |
| 2.4 | 发现调度器 | 启动异步执行、`POST /api/agents/discover`、结果写 `agent_registry` |
| 2.5 | 九态机 | 状态迁移 + `agent_status_history` |
| 2.6 | 心跳 | 定时探测（默认 60 s），更新 `last_heartbeat_at` |
| 2.7 | 能力初始化 | 按需求预置三套能力（source=CONFIG），支持权重修改 |
| 2.8 | Web：Agent 管理页 + 能力配置页 | 表格、状态色、健康检查按钮、能力权重编辑 |

### 验收标准
```bash
curl -X POST localhost:18080/api/agents/discover -H "Authorization: Bearer $T"
# 等 10 s
curl -s localhost:18080/api/agents -H "Authorization: Bearer $T" | jq '.data.records[] | {agentCode,status,version,protocol}'
```
必须满足：
1. 三个 Agent 都能被发现，`executablePath` 指向 `/home/wangchong/...` 而**不是** `/mnt/d/...`。
2. 若某个未装，状态必须是 `NOT_INSTALLED` 而不是"在线"。
3. 若装了但跑不起来（如 shim），状态是 `ERROR` 且 `lastError` 含 `Exec format error`。
4. 健康检查后状态从 `INSTALLED` → `ONLINE`（或如实报 `UNLICENSED`）。
5. Web 页面能看到上述所有字段，能力权重可改并持久化。

### 关键风险
- 凭据探测不能读 `~/.claude.json` 里的 phone/token 内容，只判断文件存在与 mtime。**探测代码严禁打印凭据内容。**

## 阶段三：ACP 通信与单 Agent 执行

### 目标
Hub 能通过 ACP 打开一个真实会话，让 Agent 读取指定项目目录、完成一个简单代码任务，并拿到结构化日志与最终结果。

### 任务分解

| # | 任务 | 说明 |
| --- | --- | --- |
| 3.1 | JSON-RPC 编解码层 | NDJSON、id 分配、错误映射、超时、背压 |
| 3.2 | 进程管理 | `ProcessBuilder`、stderr 线程、优雅关闭、僵尸回收 |
| 3.3 | ACP 客户端核心 | `initialize` / `session/new` / `session/prompt` / `session/cancel` |
| 3.4 | 事件流 | `session/update` → 内部 `AgentEvent`（message/tool/plan/file） |
| 3.5 | 权限闸门 | `session/request_permission` → 审批引擎（本期先做"策略直通/拒绝"，UI 后续接） |
| 3.6 | 会话持久化 | `agent_session`、心跳、崩溃标记 |
| 3.7 | 超时与取消 | 空闲 5 min / 硬 60 min；取消后 SIGTERM→5 s→SIGKILL |
| 3.8 | 日志落盘 | 原始 NDJSON 全量写文件，摘要写 DB |
| 3.9 | 单 Agent 执行 API | `POST /api/tasks` 走"不调度"模式直接指定 Agent 执行 |

### 验收标准
```bash
# 手工建一个任务，指定 claude-code 在测试仓库执行"新增一个 hello.txt"
curl -X POST localhost:18080/api/tasks -d '{"title":"probe","rawRequirement":"在仓库根创建 hello.txt，内容为 hello","projectId":"<test>","primaryAgentId":"<claude>","autoDispatch":false}'
# 观察
curl -N localhost:18080/api/sse/tasks/<id>
```
必须满足：
1. 会话真实建立，`agent_session.acp_session_id` 非空。
2. 能看到流式事件（不是等 5 分钟后一次性出现）。
3. 文件真的被创建，`git status` 可见。
4. 中途 `cancel` 能立即停住，进程确实退出（`ps` 无残留）。
5. 原始报文日志可在 `~/ai-hub/logs/` 找到，能复现问题。

### 关键风险与缓解
| 风险 | 缓解 |
| --- | --- |
| 协议版本不一致导致握手失败 | 握手失败即降级 CLI 适配器，并记录 `protocolVersion` |
| 某些适配器不实现 `fs/*` | 客户端方法声明为"可选能力"，缺失时由 Hub 自己读写文件后把内容放进 prompt |
| 中文路径/编码问题 | 全链路 UTF-8，进程 `LANG=C.UTF-8` |

## 阶段四：任务调度中心

### 目标
用户提需求，系统自动判定复杂度、拆解、选 Agent、排队、重试，全过程可追溯。

### 任务分解

| # | 任务 |
| --- | --- |
| 4.1 | 意图识别与项目定位（LLM 调用 + 规则兜底） |
| 4.2 | 复杂度判定（SIMPLE/MEDIUM/COMPLEX）与任务类型分类 |
| 4.3 | 任务拆解（生成 `plan_json` 与 `hub_task_step`） |
| 4.4 | 调度打分器（5 维加权，可配置） |
| 4.5 | 决策记录（候选集、分数、淘汰原因落 `dispatch_reason` + `hub_task_agent.score_detail`） |
| 4.6 | 队列（Redis ZSET + DB 对账）与并发信号量 |
| 4.7 | 状态机（十态、乐观锁、非法迁移拦截） |
| 4.8 | 重试策略（同 Agent N 次 → 换 Agent → 人工） |
| 4.9 | 多 Agent 协作（主执行 + 复核，REVIEWER 角色） |
| 4.10 | 依赖执行（step 的 `depends_on` 拓扑排序） |
| 4.11 | Web：任务列表 + 任务详情（含决策理由展示） |

### 验收标准
1. 给一个"简单任务"，只派 1 个 Agent，任务完成。
2. 给一个"中等任务"，主 Agent 执行 + 第二 Agent 复核，两条 `hub_task_agent` 记录。
3. 把唯一可用 Agent 的 `max_concurrency` 设为 0，提交任务 → 进入 `QUEUED` 而非报错；放开后自动执行。
4. 让 Agent 故意失败 → 按策略重试 → 换 Agent → 最终 FAILED 且 `error_message` 可读。
5. 任务详情页能看到"为什么选这个 Agent"（候选、得分、淘汰原因）。
6. 提交一个系统不支持的任务类型（如"帮我订机票"）→ 明确返回"不支持"且**不创建任务、不假装成功**。

## 阶段五：项目管理与 Native Runner

### 目标
注册明景 PMS，让 Agent 在独立 Worktree 中改代码，执行 Maven 构建与测试，产出 Diff 与报告，**原工作区零污染**。

### 任务分解

| # | 任务 |
| --- | --- |
| 5.1 | 项目 CRUD + 路径强校验（拒绝 `/mnt/*`、`\\\\wsl*`） |
| 5.2 | 项目配置（键值）+ 规则文件读取 |
| 5.3 | Worktree 管理（`git worktree add -b hub/task-xxxxx`，结束清理） |
| 5.4 | 双 JDK 注入（按 `project.jdk_version` 设置 `JAVA_HOME`/`PATH`） |
| 5.5 | 构建执行器（`mvn -o -DskipTests compile`，超时、日志落盘） |
| 5.6 | 测试执行器（`mvn -o test`，解析 surefire 汇总） |
| 5.7 | 前端构建（`npm ci && npm run build`，可选） |
| 5.8 | Diff 与文件清单（`git diff --stat`、`--name-status`、完整 unified diff 落文件） |
| 5.9 | 验收判定（build+test 都过才允许 SUCCESS） |
| 5.10 | 报告生成（Markdown：需求、分析、计划、执行、Diff、构建、测试、结论） |
| 5.11 | 清理与保留策略（失败任务保留 N 天便于排查，成功任务 24 h 清理） |
| 5.12 | Web：项目管理 + 项目配置 + 任务详情 Diff 视图 |

### 验收标准
```bash
# 记录基线
git -C /home/wangchong/projects/mgiot-pms status --short   # 必须为空
git -C /home/wangchong/projects/mgiot-pms branch --show-current

# 提交任务 → 等待完成
# 再次检查原工作区
git -C /home/wangchong/projects/mgiot-pms status --short   # 仍必须为空！
git -C /home/wangchong/projects/mgiot-pms worktree list    # 任务结束后不应残留

# 任务产物
ls /home/wangchong/ai-hub/logs/tasks/<taskId>/
curl -s localhost:18080/api/tasks/<id>/report -H "$T" | head -50
```
必须满足：
1. 原 PMS 工作区文件与分支完全未变。
2. Worktree 内构建成功，日志里有 `java version "17"`（证明双 JDK 生效）。
3. `mvn -o test` 结果被正确解析（PMS 基线 23 类/181 用例，允许因任务改动而增加）。
4. Diff 完整可见，`/api/tasks/{id}/diff?format=files` 返回文件清单。
5. 故意制造编译错误 → 任务判定 `FAILED`，`build_result=FAILED`，报告含首条错误行。
6. 报告是真实数据，无占位符。

## 阶段六：WeClaw 微信接入

### 目标
微信私聊能进 Hub、能派 Agent、能收到结果、能审批，全程不需要用户手动切 Agent。

### 任务分解

| # | 任务 |
| --- | --- |
| 6.0 | **R1 前置验证**：抓 WeClaw HTTP 请求体，确认是否带发送者 ID 与消息 ID |
| 6.1 | WeClaw 部署（Release 二进制 + systemd user service + `~/.weclaw/config.json`） |
| 6.2 | 人工扫码登录，验证 `weclaw status` |
| 6.3 | `/v1/chat/completions` 实现（stream/非 stream、鉴权、幂等、白名单） |
| 6.4 | 渠道会话映射（`hub_channel_session`） |
| 6.5 | 主动推送（`POST 127.0.0.1:18011/api/send`）+ 失败降级重试 |
| 6.6 | 命令分发（`/help` `/agents` `/status` `/tasks` `/projects` `/cancel` `/approve`） |
| 6.7 | 进度推送去抖（3 s 窗口合并） |
| 6.8 | 连接状态监控与掉线告警（微信推送 + Web 状态） |
| 6.9 | 掉线后人工重扫流程（文档 + Web 提示） |
| 6.10 | Web：微信连接管理页（状态、最近消息、测试发送） |

### 验收标准
1. 手机发"帮我看下 PMS 最近有什么改动"，手机 2 秒内收到受理语。
2. 任务完成后手机收到结果摘要。
3. 发 `/agents` 收到三个 Agent 状态。
4. 发 `/cancel TASK-xxxxx` 能取消。
5. 单元测试：模拟两个不同 `external_user_id` 的消息，验证 `conversation_id` 不同（会话隔离）。
6. 拔网线 → 渠道状态转 `ERROR` → 恢复后自动重连或给出明确提示。
7. 非白名单微信号发消息 → 收到"无权限"，且**不产生任务**。

### 若 R1 验证失败
按《项目可行性分析》R1 降级：单账号单会话映射，明确告知用户"暂不支持多用户"。**不得为了验收通过而伪造发送者 ID。**

## 附：绝对不做

1. 一次性生成全部模块代码。

6. 在未验证的第三方协议上编造实现。
